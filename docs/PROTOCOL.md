# 실험 프로토콜

이 문서는 결과를 믿을 수 있게 만드는 규칙이다. 알고리즘이 좋아 보이는 것과 실험으로 좋다고 확인된 것은 다르다.

## 1. 비교 조건과 통제

| 조건 | 설명 |
|---|---|
| `no_retrieval` | 외부 지식 없이 같은 생성 모델로 답한다 |
| `vanilla_rag` | 후보에서 검색 점수 상위 k개를 고른다(기준선) |
| `kore` | 같은 후보, 같은 k, 같은 토큰 예산에서 `kore` 선택기를 쓴다 |
| `kore_ablate_<특징>` | `kore`에서 `coverage`, `diversity`, `redundancy`, `reliability` 중 하나를 끈다 |
| `gold_context` | **진단용.** 정답 근거 문서를 직접 준다(상한선). 방법 비교에 쓰지 않고, 질문·루브릭·모델이 정상인지 보는 데만 쓴다 |

모든 조건에서 고정하는 것: 후보 목록(한 질문당 한 번만 검색해서 공유), `k`, 토큰 예산, 프롬프트(`kore.generation.build_prompt`),
디코딩(greedy), seed, 생성 모델 버전. 그래프·기억·예측기 제거 실험은 그 부품이 구현된 뒤에 같은 방식으로 추가한다.

## 2. 사전 등록

실험을 돌리기 **전에** `docs/prereg/YYYY-MM-DD_이름.md`를 만들어 아래를 적고, 나머지 두 사람이 읽고 승인한다. 결과를 본 뒤에는 이 파일을 고치지 않는다.

```markdown
# 사전 등록: (실험 이름)
- 날짜 / 작성자 / 승인자:
- 질문(RQ)과 가설(H):
- 주 지표 한 개(예: test 분할 rubric 점수의 kore - vanilla_rag 쌍체 차이):
- 부 지표:
- "효과가 있다"고 부를 기준(예: 쌍체 95% 구간의 하한이 0보다 크다):
- 기준을 못 넘으면 쓸 문장("효과를 확인하지 못했다"):
- 사용할 데이터 버전(knowledge/evaluation 파일 해시), 생성 모델, seed, k, 토큰 예산:
- 알려진 한계:
```

주 지표를 하나만 정하는 이유는 여러 지표 중 좋아 보이는 것만 고르는 일을 막기 위해서다.

## 3. 분할 사용 규칙

- `train`: 선택기 학습, 가중치 탐색.
- `dev`: 가중치 선택과 설계 결정.
- `test`: **최종 평가 한 번.** 코드가 `--final-test`를 켜야만 test를 돌리고, 튜닝 함수(`grid_search_weights`)는 test를 받으면 오류를 낸다.
  test 결과를 보고 알고리즘을 고치면 그 test는 더 이상 test가 아니다. 그때는 새 test를 만들어야 한다.
- 선택기를 학습하거나 경험을 기록할 때도 test 질문은 쓰지 않는다(`ExperienceLog`가 거부한다).

## 4. 닫힌북 필터와 측정 잡음

- 모델이 근거 없이 맞히는 질문은 `no_retrieval`에서 이미 정답이라 지식의 기여를 잴 수 없다.
  dev 분할에서 `no_retrieval` 정답률을 먼저 재고, 높은 질문은 빼거나 별도 층으로 보고한다.
- 생성은 greedy로 고정해서 확률적 잡음을 없앤다. 그래도 모델·프롬프트가 바뀌면 값이 달라지므로 둘 다 기록한다.
- rubric 키워드 점수는 의미 평가가 아니다. 일부(예: 30개)는 답변의 출처를 가린 채 사람이 채점해서 자동 점수와의 일치도를 확인한다.
- 생성 모델이 자기 답변을 채점하게 하지 않는다(자기 선호 편향).

## 5. 통계와 표본 크기

- 모든 지표는 평균과 함께 부트스트랩 95% 구간을 낸다(`results.csv`). 조건 비교는 같은 질문끼리 짝지은 차이와 구간을 낸다(`comparisons.csv`).
- test가 작으면 작은 차이는 구분할 수 없다. 쌍체 비교에서 검출 가능한 최소 차이는 대략
  `(1.96 + 0.84) × (질문별 차이의 표준편차) / √n` 이다. 질문별 차이의 표준편차를 0.55(질문의 30% 정도가 두 조건에서 엇갈리는 경우)로 가정하면 n=24에서 약 0.31, n=60에서 약 0.20, n=120에서 약 0.14다.
  `kore.evaluation.approx_mde`로 직접 계산해 볼 수 있다. 표준편차는 가정이므로 dev 결과로 다시 추정한다.
- 따라서 "구간이 0을 포함한다"는 "차이가 없다"가 아니라 "이 표본으로는 구분하지 못했다"로 쓴다.

## 6. 주 지표와 판정 문장

- 주 지표: test 분할에서 `kore`의 rubric 점수 − `vanilla_rag`의 rubric 점수, 같은 질문끼리 짝지은 평균 차이와 부트스트랩 95% 구간. 하나만 정한다.
- 구간 하한 > 0이면 "이 데이터에서 효과를 확인했다", 상한 < 0이면 "해롭다", 아니면 "이 표본으로는 구분하지 못했다".
- 제거 실험과 분야별 결과는 탐색용이다. 주 결론에 쓰지 않는다.

## 7. 분야 게이트 (G2)

`kore run --conditions no_retrieval vanilla_rag gold_context`를 train·dev에서 돌린 뒤 `kore screen --run-dir ...`.
기준: `no_retrieval` ≤ 0.5(모델이 이미 알면 지식의 기여를 못 잰다), `gold_context` ≥ 0.6(낮으면 질문·루브릭·모델 문제), 후보 재현율 ≥ 0.8(낮으면 검색부터 고친다).
분야마다 채점된 질문이 5개 미만이면 "보류"다. 기준값은 처음 정한 값이고 dev 결과를 본 뒤 바꾸려면 이유를 DECISIONS에 적는다.

## 8. 기여도 라벨링(ΔQ)과 H1 판정

- 점수 = 짧은 `reference_answer`의 평균 로그확률(근거 부분집합을 줬을 때). 단일 이득 = s(부분집합) − s(없음), 쌍 시너지 = s(a,b) − s(a) − s(b) + s(없음).
- 열린 모델(`--generator hf`)만 쓴다. train·dev만 라벨링하고 test는 거부한다.
- 보는 값: 순위-이득 스피어만 상관(귀무 0), 1위 불일치율(귀무 1−1/m), `capture_ratio`(0 = 무작위, 1 = 최선), 시너지 비율, "최선 문서에 더하면 나빠지는" 비율.
- `oracle_gap`은 최댓값이라 항상 0 이상이다. 그 자체로는 증거가 아니다. 귀무값과 비교한 값만 해석한다.
- 로그확률은 포화할 수 있어서 음의 시너지가 측정 인공물일 수 있다. 결과가 이상하면 `reference_answer` 길이와 점수 분포부터 본다.
- 제안 판정(사전 등록에서 확정): 질문 20개 이상이고 `capture_ratio`의 95% 구간 상한이 0.8 미만이면 H1 신호로 보고 계속한다. 아니면 H3로 가지 않는다.

## 9. 사람 블라인드 채점

`kore blind-export`로 채점표(`blind_sheet.csv`)와 키(`blind_key.csv`)를 만든다. 채점자 2명이 따로 0/1/2로 채점하고, `kore blind-score`가 가중 카파와 자동 점수와의 순위상관을 낸다. 키는 채점 전에 열지 않는다.

## 10. 보고 규칙

- 결과 폴더에는 항상 산출 보고서를 함께 둔다. 숫자만 남기지 않는다.
- 이긴 설정만 보고하지 않는다. 시도한 설정 수와 실패한 설정도 적는다.
- 실패 사례 표를 만든다: KORE가 `vanilla_rag`보다 나빴던 질문과 그 이유.
- 부정적 결과와 효과 없음은 그대로 쓴다. 성능 향상이나 독창성은 사전 등록한 기준을 넘었을 때만 주장한다.
- 선행연구와 겹치는 부분은 겹친다고 쓴다. 원 논문의 구현을 재현한 것과 직접 구현한 것을 구분해서 적는다.
