# 3차 산출 보고서: 검색 강화와 시작 안내 (2026-10-24)

요청: 분야 확인, 데이터 공개 장단점, GitHub 연결 안내, 성능 강화, 바로 따라 할 수 있는 실행 안내.

## 0. 먼저 읽을 네 가지

1. **성능을 잰 곳은 우리 데이터가 아니라 공개 데이터 KorQuAD 1.0 dev다.** 우리 데이터는 아직 없다. 여기서 본 검색 개선이 우리 데이터에서도 나온다는 보장은 없다.
2. **검색 개선은 작고 실제로 확인됐다.** 조사 떼기 토크나이저가 Recall@1을 0.879 → 0.886 올렸다(질문 5,774개, McNemar z = 3.2).
3. **KORE 선택기의 기본 중복 벌점이 근거 하나짜리 질문에서 오히려 손해였다.** 0.5 → 0.1로 낮췄다. 이건 KORE가 vanilla보다 낫다는 증거가 아니라 "덜 해롭게" 고친 것이다.
4. **임베딩 하이브리드 검색은 코드만 있고 아직 한 번도 진짜 모델로 돌리지 못했다.** torch가 없고 Hugging Face에 접속이 안 되는 환경이었다. 노트북 02의 2-1 셀이 첫 확인이다.

## 2. 검증한 것

- 전체 테스트 **226개 통과**: 파이썬 3.10, 3.11, 3.12, 3.13. (2차 때 못 했던 3.10을 이번에 따로 설치해서 확인했다.)
- KorQuAD 1.0 dev에서 토크나이저 변형 6개, BM25 매개변수 4쌍, 중복 벌점 4값을 비교했다. 결과는 `DECISIONS.md` 13절 표.
  - 라이브러리에 넣은 `ngram_stem`이 실험 코드와 같은 숫자(R@1 0.8855)를 내는지 다시 돌려 확인했다.
- 하이브리드의 섞는 계산은 "같은 뜻 낱말을 같은 차원으로 모으는" 가짜 인코더로 시험했다: BM25가 놓친 바꿔 말하기 문서를 찾는지, alpha=1이면 BM25 순서와 같은지, 분야 필터, 문서는 한 번만 인코딩하는지, 모든 조건이 같은 후보를 공유하는지.
- 노트북 03의 3-B(문서 올리기), 3-C(분할 두 번: 처음, 그다음 `--keep-from`) 셀을 이 환경에서 경로만 바꿔 실제로 실행했다. 업로드·다운로드 셀은 Colab 전용이라 못 돌렸다.
- 가짜 데이터로 `run → screen → search`를 새 기본값으로 다시 돌렸다(이 숫자는 연구 결과가 아니다).
- GitHub 안내의 사실(웹 업로드 100개·25MiB, 비공개 무료 저장소 보호 규칙 불가, 조직 토큰 기본 관리자 승인, Actions 월 2,000분, `gh repo create` 문법, `gh` 설치 명령)은 공식 문서를 열어 확인했다. 출처는 `DECISIONS.md` 14절.

## 4. 바꾼 기본값과 그 영향

`CLAUDE.md` 규칙 6에 따라 적는다. 실제 연구 결과가 아직 없어서 이전 결과와 섞일 일은 없다.
- 토크나이저 기본값 `ngram` → `ngram_stem`. 설정 해시가 바뀌므로 이전에 돌린 `results/` 폴더에 이어서 돌리면 러너가 막는다(의도한 동작).
- 중복 벌점 0.5 → 0.1. 거의 같은 문서 두 개가 함께 뽑힐 수 있다. 그래서 거의 같은 문서는 `kore stats`의 중복 점검으로 데이터에서 먼저 없앤다.
- 검색기 기본값은 그대로 BM25다. 하이브리드는 확인 전까지 켜지 않는다.
