## 1. 언어: 한국어로 시작한다

- 질문이 120개 안팎이라 두 언어로 나누면 언어마다 60개가 되고, 작은 차이를 구분하기가 더 어려워진다(4절 표).
- B와 C가 한국어 자료를 읽고 쓰는 속도와 정확도가 영어보다 높다. 데이터 품질이 먼저다.
- 한국어 소형 모델이 영어보다 약할 수 있다. 그래서 모델의 한국어 독해를 첫날 GPU 점검 셀(`notebooks/02`)로 직접 잰다. 이 결과가 G1이다.
- 영어를 붙이는 방법: 같은 코드, 같은 평가로 영어 자료 한 분야를 따로 만들어 "한국어에서 본 결과가 영어에서도 나오는가"만 본다. 한국어 결과와 합치지 않는다.
- 코드는 두 언어를 이미 읽는다(`tokenize.py`). 다만 실제 한국어 자료에서 BM25 후보 재현율이 어떤지는 아직 모른다. 그것도 G3에서 잰다.

- 선택 이유: 무료 Colab GPU(보통 T4, 보장 없음)에 올라가는 크기이고, 로그확률을 직접 계산할 수 있다. 4B 모델은 float16으로 약 8GB(계산값, 실측은 노트북이 한다).
- T4는 bfloat16을 기본 지원하지 않아서 float16으로 둔다. float16에서 출력이 깨지는 모델이 있으므로 첫 실행의 점검이 필요하다. 이건 확인 못 했다.
- EXAONE은 모델 저장소의 코드를 실행해야 하므로(`trust_remote_code`) 모델 카드를 읽고 켠다. 접근 동의 화면이 뜨는지도 확인 못 했다.
- Qwen3-4B는 `transformers` 4.51 이상이 필요하다(모델 카드, 확인함). 노트북이 맞춰 설치한다.
- **확인 못 한 것**: 이 환경에는 GPU와 torch가 없어서 모델 로딩, 생성, 로그확률 계산 코드를 실제로 돌려 보지 못했다. 프롬프트 조립과 설정 검사까지만 테스트했다. `notebooks/02_colab_gpu_run.ipynb`의 2번 셀이 첫날 이걸 확인한다.

### GPT·Claude·Gemini를 안 쓰는 이유

1. 돈이 든다. 질문 120개 × 조건 4개만 해도 호출이 수백 번이고, 기여도 라벨링은 질문당 22~93번이라 수천 번이다.
2. 기여도 라벨링(P1)은 정답 문장의 로그확률이 필요하다. 이 값을 주는 API는 드물고, 주더라도 전체 토큰 분포는 막혀 있는 경우가 많다. (일반 지식이고 이번에 제공사별로 확인하지는 않았다.)
3. 같은 모델 이름이어도 시간이 지나면 내용이 바뀐다. 오픈 모델은 `revision`(커밋 해시)으로 고정해서 같은 결과를 다시 만들 수 있다.
4. 마스터 문서 3절도 "실제 모델 API 없이도 돌아야 한다"고 적었다.

무료 웹 채팅(GPT, Claude, Gemini)은 자동으로 돌릴 수 없고 모델과 시스템 프롬프트가 바뀌어도 알 수 없어서 실험 조건으로 쓰지 않는다. 쓸 수 있는 곳은 두 군데뿐이다.
오타와 어색한 문장 점검, 그리고 "이 질문이 애매하지 않은가"를 사람이 확인할 때의 두 번째 눈이다. 질문을 AI에게 대량으로 만들게 하지 않는다(근거 문장을 베낀 질문이 나와서 검색 성능이 부풀려진다). 답변 채점도 AI에게 시키지 않는다.

## 4. 규모, 분할, 표본 크기

- 문서 약 200개(분야당 65개 안팎, 100~1500자). 마스터 문서의 150~300개 범위 안이고, 질문 120개의 정답 근거(근거 둘 이상 질문 포함)와 방해 문서를 충분히 두기 위한 숫자다.
- 질문 120개(분야당 40개). 난이도는 easy 30% / medium 40% / hard 30%. 근거가 둘 이상인 질문을 30% 이상(36개 이상) 넣는다. H2는 이런 질문이 있어야 볼 수 있다.
- 분할 50/20/30, 분야별 층화. 질문을 더 만들어 다시 나눌 때는 `kore split --keep-from data/evaluation.csv`로 기존 질문의 분할을 고정한다(이미 튜닝·라벨링에 쓴 질문이 test로 넘어가는 것을 막는다). 이 옵션 없이 기존 파일을 덮어쓰려 하면 명령이 거부한다. 마스터 문서는 분할 비율을 정하지 않았다. test를 36개로 늘리려는 선택이다. 학습 기반 선택기(H3)는 신호가 있을 때만 하므로 train을 줄여도 손해가 작다.

쌍체 비교에서 검출할 수 있는 최소 차이(`kore.evaluation.approx_mde`, 검정력 80%, 유의수준 5%). 질문별 차이의 표준편차(sd)는 가정이다. dev 결과로 다시 어림한다.

| test 질문 수 | sd 0.55 | sd 0.40 | sd 0.30 |
|---|---|---|---|
| 24 | 0.32 | 0.23 | 0.17 |
| 36 (이 계획) | 0.26 | 0.19 | 0.14 |
| 60 | 0.20 | 0.15 | 0.11 |
| 120 | 0.14 | 0.10 | 0.08 |

test 36개로는 rubric 점수가 0.2~0.26 이상 차이 나야 구분된다. 선택기 하나가 만드는 차이가 그보다 작을 가능성이 크다.
그래서 **주 결과가 "구분하지 못했다"로 나올 수 있다**. 그것도 정직한 결과이고, 그 경우 H1 라벨링 분석(6절)이 연구의 중심이 된다.
rubric 항목을 질문당 2~3개로 두는 것도 같은 이유다. 항목이 1개면 점수가 0 아니면 1이라서 분산이 크다.

## 5. 지표와 판정 기준

- 주 지표(하나): test 분할에서 `kore`의 rubric 점수 − `vanilla_rag`의 rubric 점수, 같은 질문끼리 짝지은 평균 차이와 부트스트랩 95% 구간.
- 판정: 구간 하한이 0보다 크면 "이 데이터에서 효과를 확인했다". 상한이 0보다 작으면 "해롭다". 둘 다 아니면 "구분하지 못했다". 이 문장은 결과를 보기 전에 사전 등록 파일에 적는다(`docs/PROTOCOL.md` 2절).
- 부 지표: 선택된 문서의 정답 근거 Recall@3, 컨텍스트 토큰 수, 지연시간, 사람 블라인드 점수(30개 답변, 채점자 2명).
- 제거 실험(ablation)과 분야별 결과는 탐색용이다. 여러 개를 보면 우연히 좋아 보이는 것이 나오므로 주 결론에 쓰지 않는다.
- rubric 점수는 키워드 일치라서 의미 평가가 아니다. 그래서 사람 블라인드 채점으로 자동 점수와의 일치도를 같이 본다.

## 6. 연구 순서

1. 기준선: 데이터를 만들고 `no_retrieval`, `vanilla_rag`, `kore`를 같은 조건으로 돌린다. `gold_context`(정답 근거를 직접 주는 상한선)는 질문과 모델이 정상인지 보는 진단용이다.
2. **3주차 갈림길(G4)**: `kore label`로 dev 질문의 기여도 라벨을 만들고(후보 6개·크기 2까지, 질문당 22번) `kore label-report`로 본다. 제안 기준: 질문이 20개 이상이고 `capture_ratio`의 95% 구간 상한이 0.8보다 작으면(유사도 상위 k가 최선과 무작위 사이 간격의 80%에 못 미침) H1 신호가 있다고 보고 계속한다. 아니면 H3로 가지 않고, 가중치 선택기 비교와 부정적 결과 보고로 정리한다. 기준은 사전 등록에서 확정한다.
3. 신호가 있을 때만 후보를 8개·크기 3까지 넓혀 H2(시너지)를 본다. H3(학습)은 그 뒤다.

H1을 먼저 하는 이유는 가장 싸고(학습이 필요 없다) 결과가 나쁘게 나와도 정보가 되기 때문이다.
선행연구 겹침은 초록 수준에서만 확인했다. H2는 Shapley 기반 RAG 귀속 연구(arXiv 2507.04480)와 가장 가깝고, H1은 ContextCite와 BAR-RAG, H3는 GAM-RAG와 BAR-RAG와 가깝다.
원문은 B가 읽어야 하고, 읽기 전에는 독창성을 주장하지 않는다.

## 11. 데이터 공개 (5주차 사전 등록 때 결정)

공개를 목표로 두면 연구 결과(선택기가 이기든 지든)와 상관없이 남는 것이 생긴다. 대신 조건이 붙는다.

| | 장점 | 단점·비용 |
|---|---|---|
| 남는 것 | 근거 문서와 모범 답안이 붙은 한국어 질문 세트는 다른 사람이 자기 검색 방법을 시험할 때 쓸 수 있다. 부정적 결과도 재현 가능해진다 | 누가 쓸지는 장담 못 한다. 한국어 RAG 평가 데이터가 이미 얼마나 있는지 아직 조사하지 않았다(B가 확인) |
| 신뢰 | 남이 숫자를 다시 계산해 볼 수 있어서 결과를 믿을 근거가 생긴다 | 실수(정답이 틀린 질문, 잘못 자른 문서)도 같이 드러난다. 공개 전 전수 점검이 필요하다 |
| 라이선스 | `law`(법령 조문)와 `guide`(공공누리 제1유형)는 출처만 밝히면 재배포가 자유로운 편이다 | `wiki`는 CC BY-SA라서 그 부분을 공개하면 같은 조건(동일조건변경허락)을 붙여야 한다. 위키 원문에서 만든 질문의 라이선스도 따져야 한다. 이건 확인 못 한 해석이라 B가 위키 저작권 안내를 읽고 정한다 |
| 오염 | | 공개된 test 질문은 앞으로 나올 모델이 학습할 수 있다. 공개 뒤 이 test로 새 모델을 재면 점수가 부풀 수 있다. 공개본에 "공개일 이후 학습된 모델은 오염 가능"을 적는다 |
| 일 | 데이터 카드(무엇을, 어떻게 모았고, 무엇에 쓰면 안 되는지)를 쓰면 보고서의 방법 절이 거의 같이 끝난다 | 데이터 카드와 정리에 하루~이틀 더 든다 |
| 법령 주의 | | 법령은 개정된다. 확인일과 시행일을 데이터에 남기고, "법률 상담이 아니다"를 적는다 |

제안: 3분야 그대로 연구하고, 공개는 `law`와 `guide`만 먼저 한다. `wiki`는 B가 라이선스를 확인한 뒤 같은 조건으로 낼지 뺄지 정한다. 공개 결정은 결과를 보기 전(5주차 사전 등록 때)에 해 둔다. 결과가 좋을 때만 공개하면 그것도 선택 편향이다.

## 12. 저장소 주인과 공개 범위

- 저장소는 A 개인 계정이 아니라 **무료 조직** 아래 만든다. 개인 저장소에 초대된 사람은 그 저장소용 세분화 토큰을 만들 수 없어서 B, C가 Colab에서 저장소를 받지 못한다. 조직은 멤버가 각자 토큰을 만들고 A가 승인한다(기본 설정이 관리자 승인, GitHub 문서 확인함).
- **비공개 무료 저장소에서는 `main` 보호 규칙을 쓸 수 없다**(GitHub 문서 확인함). "PR로만 합친다"는 셋이 약속으로 지킨다. 공개로 바꾸면 보호 규칙을 쓸 수 있지만 11절의 문제가 생긴다.
- 단계별 방법은 `docs/START.md`.

## 13. 성능 강화 (2026-10-24)

우리 데이터가 아직 없어서 공개 한국어 데이터 KorQuAD 1.0 dev(문단 964개, 질문 5,774개, CC BY-ND 2.0 KR이라 저장소에 넣지 않고 로컬 평가에만 썼다)로 쟀다.
KorQuAD 질문은 문단을 보고 쓴 것이라 우리 질문보다 낱말이 많이 겹친다. 그래서 우리 데이터에서의 효과는 더 크거나 작을 수 있다.

| 변경 | KorQuAD 결과 | 결정 |
|---|---|---|
| 토크나이저 `ngram` → `ngram_stem`(조사·어미를 뗀 어간 추가) | 전체 Recall@1 0.879 → 0.886(새것만 맞힘 82, 이전만 맞힘 46, McNemar z = 3.2). 표현이 많이 바뀐 질문 2,754개에서 0.809 → 0.824(z = 3.9) | 기본값으로 바꿈. 변형 6개를 시험하고 골랐으므로 선택 편향이 조금 있다(z가 다중 비교를 견딜 만큼 크다) |
| 2-gram에 3-gram 추가 | 나빠짐(R@1 0.862) | 안 씀 |
| BM25 k1, b 바꾸기 | 차이 0.01 안팎, 일관되지 않음 | 그대로 둠 |
| `kore` 선택기의 중복 벌점 0.5 → 0.1 | 근거 하나짜리 질문에서 0.5는 정답 문단을 밀어냈다: R@3 0.9652(유사도 선택 0.9687보다 낮음, z = −2.3). 0.1은 0.9695 | 기본값 0.1로 바꿈. 같은 글의 문단끼리 비슷해서 정답이 "중복"으로 벌점을 받은 것으로 보인다. 근거가 둘 이상인 질문에서 0.1이 충분한지는 모른다 |
| 임베딩 하이브리드(BM25 + `intfloat/multilingual-e5-small`) | 이 환경에 torch가 없어 **재지 못했다** | 선택 사항으로 넣음. 노트북 02의 2-1 셀이 우리 train·dev에서 BM25와 비교한다 |

이 표는 우리 연구 결과가 아니다. 검색 단계의 기본값을 정한 근거일 뿐이고, KORE가 vanilla RAG보다 낫다는 뜻이 아니다. 근거 하나짜리 질문에서는 `kore`가 유사도 선택과 같은 수준(0.9695 대 0.9687, 차이 없음)이라는 것까지만 보였다.
