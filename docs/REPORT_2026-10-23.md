# KORE 인계 문서 검토·구현 보고서

작성일 2026-10-23 · 대상 문서 「KORE 프로젝트 AI 인계용 마스터 문서 v1.0」 · 코드 버전 0.1.0 · 데이터 계약 1.0

이 보고서는 인계 문서를 읽고 (1) 확정된 결정과 미검증 가설을 나누고, (2) 기술적 실현 가능성을 따져 보고, (3) 48시간 분량의 저장소와 코드를 실제로 만들어 돌려 본 결과를 적는다.
기존 계획은 바꾸지 않았다. 바꾸는 게 낫다고 본 곳은 4절에 근거와 함께 제안으로만 적었다.

## 0. 먼저 읽을 다섯 가지

1. **만든 것은 돌아간다.** 테스트 146개가 파이썬 3.11, 3.12, 3.13에서 통과하고, 일부러 심은 결함 10개를 테스트가 전부 잡았으며, 새 가상환경에서 `pip install -e ".[dev]"`도 깨끗하게 된다. (6절)
2. **가장 큰 위험은 독창성이다.** 세 가설 모두 가까운 선행연구가 있다. 특히 H2(지식 조합 효과)는 RAG 문서 기여도를 Shapley 값으로 재면서 중복·상호보완·시너지를 평가한 연구와 정면으로 겹친다. 초록만 읽은 판단이라 본문 확인이 필요하다. (3절)
3. **KORE 선택기가 vanilla보다 낫다는 증거는 아직 없다.** 샘플 7문항에서 한 문제도 더 낫지 않았고, k=2에서는 한 문제를 더 놓쳤다. 샘플이 작아서 결론은 아니지만, "기본 가중치로 이미 낫다"고 말할 근거는 없다. (6절)
4. **질문 100~120개로는 큰 차이만 구분한다.** test가 24개이면 쌍체 비교로 검출 가능한 최소 차이가 0.3 안팎이다. 5%p 개선은 이 표본으로 확인할 수 없다. (2절)
5. **병목은 검색이 아니라 생성이다.** 문서 300개·질문 120개를 7개 조건으로 돌리는 데 2.7초가 걸린다. 비용은 기여도 라벨을 만드는 언어모델 호출 횟수에서 나온다. (2절)

## 1. 확정된 것과 아직 모르는 것

### 문서가 확정했다고 적은 것 (그대로 따랐다)

| 항목 | 내용 |
|---|---|
| 팀과 환경 | 3인, 무료 Colab, 노트북 1대의 Claude Code |
| 목표 | 기존 모델에 붙이는 지식 검색·선택 엔진, 학술적 연구 지향 |
| 결과물 | 실행 코드, 평가 데이터·결과, GitHub 저장소, Gradio 데모, 보고서와 발표 자료 |
| MVP 범위 | CPU BM25, 표준 데이터 형식, 유사도 선택기와 독자 선택기 1개, 3조건 비교, 테스트와 기록, 간단한 데모 |
| 제외 범위 | 대규모 파인튜닝·강화학습, 수백만 문서, 대규모 크롤링, 멀티모달 하이퍼그래프 재현, 상용 배포 |
| 평가 조건 | no-retrieval / vanilla RAG / KORE / ablation, 같은 후보·같은 k·같은 토큰 예산 |
| 역할과 일정 | A 개발, B 데이터·연구, C 평가·재현. 6주 + 1주 버퍼 |
| 인터페이스 | `retrieve`, `select_knowledge`, `evaluate`, `KnowledgeItem`, 평가 질문 열 |

### 문서 스스로 미검증이라고 적은 것 (검증됐다고 쓰지 않았다)

- H1 유사도 순위와 실제 기여도가 어긋나는 사례가 있다.
- H2 지식 조합 효과가 개별 기여도의 합과 다르다.
- H3 과거 경험으로 학습한 선택기가 새 질문에서도 좋아진다.
- KORE가 vanilla RAG보다 낫다는 것, 그리고 독창성.
- 5절의 선행연구 링크·서지·세부 내용. 점수식의 `argmax` 수식은 일반 최적화 형태라 신규성이 없다고 문서가 직접 적었다.
- 선택 점수식(유사도·출처 신뢰도·분야 다양성·중복 패널티·질문-근거 연결)의 가중치는 설계 가설이다.

### 문서에서 모호하거나 비어 있던 것

- **숫자 표기.** "문서 150300개", "질문 100120개"는 물결표(~)가 빠진 것으로 읽었다(150~300개, 100~120개). 맞는지 확인이 필요하다.
- **13절의 미확정 5개.** A의 OS·Claude Code 설치, 세 사람의 숙련도와 주당 시간, 3개 분야와 라이선스와 언어 범위, 무료로 돌릴 생성 모델, 평가 지표의 정확한 정의. 이 중 어느 것도 내가 임의로 정하지 않았다. 샘플 분야(천문·화학·컴퓨팅)는 배관 점검용 자리표시자다. 생성 모델은 인터페이스(`Generator`)만 만들어 두었다.

## 2. 기술적 실현 가능성

| 항목 | 판정 | 근거와 남은 문제 |
|---|---|---|
| 검색·선택·평가 코드를 CPU로 | **충분히 가능** | 합성 문서 300개·질문 120개·7개 조건(840행)이 2.7초, 최대 메모리 28MB. 합성 데이터라 품질이 아니라 속도만 보여 준다 |
| 무료 Colab 환경 | **검색·선택은 가능, 생성은 불확실** | GPU 배정과 연속 실행 시간이 보장되지 않는다. 러너는 끊겨도 이어서 돌도록 만들었다. 생성 한 번의 시간은 모델과 GPU에 달려서 **측정하지 못했다** |
| 기여도 라벨(ΔQ) 비용 | **가장 큰 기술 위험** | 아래 표 |
| 표본 크기 | **작은 효과는 검증 불가** | 아래 표 |
| 평가 신호 | **설계 보강 필요** | 닫힌북 정답, 채점기 편향, 키워드 채점의 한계(PROTOCOL 4절) |
| 1주차 목표(B 문서 50개) | **빠듯함** | B가 주 10시간이면 문서 하나에 12분이다. 출처를 열어 보고 라이선스까지 확인하면 이 안에 끝내기 어렵다. 주 10시간은 문서 9절이 "권장 시간"으로 적은 값이고, 실제 가용 시간은 13절에서 미확정이다 |

**기여도 라벨의 호출 횟수.** 한 질문에서 후보 c개의 부분집합을 모두 평가하면 생성(또는 점수 계산) 횟수는 다음과 같다. 정확한 조합 수이고, 호출 하나의 시간은 모델이 정해져야 알 수 있다.

| 후보 수 c | 기준 + 단독 + 쌍 | 세 개 조합까지 |
|---|---|---|
| 6 | 22 | 42 |
| 8 | 37 | 93 |
| 10 | 56 | 176 |

질문 100개에 c=10, 세 개 조합까지 보면 한 번 도는 데 17,600번이다. 생성이 확률적이면 여기에 반복 횟수를 곱한다. c=8에 쌍까지만 보면 3,700번이다.

**검출 가능한 최소 차이.** 쌍체 비교에서 `(1.96 + 0.84) × 차이의 표준편차 / √n`로 근사했다. 질문의 30%가 두 조건에서 엇갈린다고 가정하면(표준편차 약 0.55) 다음과 같다. 이 가정은 dev 결과로 다시 추정해야 한다.

| test 질문 수 | 24 | 30 | 60 | 120 |
|---|---|---|---|---|
| 최소 검출 차이 | 0.31 | 0.28 | 0.20 | 0.14 |

인계 문서는 분할 비율을 정하지 않았다. `kore split`의 기본값인 6:2:2(내가 정한 값이다)로 나누면 질문 100~120개에서 test는 20~24개다. 이 크기에서 "KORE가 5~10%p 낫다"는 결과가 나와도 우연과 구분되지 않는다.

## 3. 독창성 점검 (초록 기준, 본문 미확인)

논문 원문이 아니라 초록 페이지만 읽었다. 겹침 판단은 "가까운 연구가 있다"까지이고, 방법이 같다는 뜻이 아니다. 본문 확인은 B의 일이다.

| 가설 | 가까운 선행연구 (초록에서 확인한 내용) | 겹침 | 남을 수 있는 차이 (가설) |
|---|---|---|---|
| H1 / RQ1 어떤 지식이 도움이 되는가 | **ContextCite**(문맥의 어느 부분이 답변을 이끌었는지 찾는 문제를 정의하고, 문맥 가지치기로 응답 품질을 높이는 활용을 보임). **BAR-RAG**(리랭커를 생성기에 맞는 근거를 고르는 경계 인식 선택기로 다시 정의, 생성기 피드백 강화학습) | 높음 | 한국어·소규모 전문 코퍼스에서의 재검증, 유사도 순위와 기여도가 어긋나는 비율의 측정 |
| H2 / RQ2 조합 효과 | **arXiv 2507.04480** (검색된 문서 단위에 Shapley 귀속을 적용하고 근사법과 비교, 중복·상호보완·시너지 관계에서 중요한 문서를 찾는지 평가) | **매우 높음** | 비용 제약 아래 소수 후보로 근사한 기여도가 실제 생성 품질과 얼마나 맞는가 |
| H3 / RQ3 경험으로 학습 | **GAM-RAG**(검색 경험을 문장 단위 기억에 쌓는 학습 없는 갱신, 칼만 필터식 이득 규칙). **BAR-RAG**(생성기 피드백으로 선택기 학습) | 높음 | 미사용 질문에서의 일반화와 기억 오염의 측정 |
| 그래프 갱신·관계 | **EvoGraph-R1**(존재만 확인, 초록 미확인). **CausalRAG2**(계층적 인과 그래프, 인과 게이팅). **SPARKLE**(지식 그래프 기반 프록시 모델이 검색 결정을 제어, 강화학습) | 해당 부품을 구현할 때 확인 | - |

링크 확인 결과: 문서 5절의 5개 논문이 모두 실재한다. SPARKLE, GAM-RAG, BAR-RAG, CausalRAG2는 문서 속 링크로 열어서 제목과 학회를 확인했고 문서의 설명과 맞았다. EvoGraph-R1은 문서의 CVPR 공식 링크가 응답하지 않아(일시 오류일 수 있다) 검색으로 CVPR 포스터 페이지와 arXiv에 있음만 확인했다. B가 직접 다시 열어 본다.

**판단.** "새로운 지식 활용 알고리즘"이라는 목표를 6주 안에 독창성으로 방어하기는 어렵다고 본다. 방어할 수 있는 쪽은 아래 같은 문장이다. 이것도 독창성이 보장된다는 뜻이 아니라, 검증 가능한 주장의 후보다.

- 기존 방법의 핵심 주장을 한국어 전문 코퍼스와 무료 Colab 예산에서 재현하고 어디서 깨지는지 정리한다.
- 소수 후보로 근사한 기여도(예: 정답 로그우도)가 실제 답변 품질과 얼마나 일치하는지 측정한다.
- 효과가 없으면 없다고, 조건과 함께 보고한다.

## 4. 수정 제안

기존 계획은 그대로 두었다. 아래는 근거가 있는 제안이고, 받아들일지는 세 사람이 정한다.

| # | 제안 | 근거 | 원안과의 차이 |
|---|---|---|---|
| P1 | 기여도 라벨은 후보를 6~8개로 줄이고 greedy 디코딩으로 고정한다. 생성 대신 **정답 답변의 로그우도**를 점수로 써 보고, dev에서 생성 품질과의 상관을 먼저 확인한다 | 2절의 호출 횟수. 로그우도는 순전파 한 번이라 생성보다 싸고 확률적 잡음이 없다. 단, 로그우도가 답변 품질을 대신한다는 보장은 없어서 상관 확인이 전제다 | 원안은 "S 유무의 답변 품질 차이". 측정 방식만 바꾸고 정의는 유지 |
| P2 | test를 60개 이상으로 늘리거나, 작게 유지하되 train+dev에서 층화 교차검증을 하고 test는 한 번만 연다. 주 지표는 사전 등록한다 | 2절의 최소 검출 차이 | 원안의 질문 수 100~120을 늘리거나 해석 방식을 바꾼다 |
| P3 | `no_retrieval`에서 이미 맞히는 질문을 dev에서 걸러 낸다 | 모델이 이미 아는 질문에서는 지식의 기여가 0이라 ΔQ를 잴 수 없다 | 추가 절차 |
| P4 | 연구 질문의 무게중심을 정하기 전에 B가 3절의 네 편(2507.04480, ContextCite, BAR-RAG, GAM-RAG)을 본문까지 읽는다. H2는 겹침이 가장 커서 문헌 조사 뒤에 남길지 정한다 | 3절 | 문서가 "겹치면 연구 질문을 수정한다"고 이미 정해 둔 절차를 앞당기는 것 |
| P5 | 1주차 B 목표를 확인한다(주당 시간이 10시간인지, 문서당 12분이 가능한지). 안 되면 50개를 30개로 낮추거나 라이선스가 명확한 공개 문서를 우선한다 | 1절·2절 | 숫자 조정 |
| P6 | 채점은 생성 모델이 자기 답변을 채점하지 않게 하고, 일부는 출처를 가린 사람 채점으로 키워드 점수와의 일치도를 본다 | 자기 선호 편향. 키워드 일치는 의미 평가가 아니다 | 문서의 "블라인드 채점도 가능하면"을 구체화 |
| P7 | ablation은 지금 구현된 4개 특징(커버리지·다양성·중복·신뢰도)을 끄는 것으로 시작하고, 그래프·기억·예측기 제거는 그 부품이 생긴 뒤에 추가한다 | 아직 없는 부품은 뺄 수 없다 | 범위 조정(구현 완료) |
| P8 | `KnowledgeItem.score`를 단계별로 분리한다 | 문서 7절의 권고 | **반영 완료** |

## 5. 구현한 것

저장소는 `kore-project/`(git 저장소, `main`과 `feature/retrieval`, `feature/selector`, `feature/evaluation` 브랜치)에 있다.

| 영역 | 내용 |
|---|---|
| 계약 | `schemas.py`, `docs/CONTRACT.md`. 열 정의, 규칙, 검증 명령, 변경 절차 |
| 검증기 | `io.py`. 필수 열, id 형식·중복, 존재하지 않는 근거 id, 분할·난이도, 정답 누출 경고, 분할 간 중복 질문 경고, 라이선스 미확인 경고. 오류가 있으면 종료 코드 1 |
| 검색 | `retrieval.py`. 외부 라이브러리 없는 BM25(손계산 값과 일치), 분야 라우팅, 한국어 조사 대응 2-gram |
| 선택 | `selector.py`. `similarity`(기준선)와 `kore`(5개 항목 가중 점수, 토큰 예산) |
| 평가 | `evaluation.py`. Recall/Precision/Hit/MRR, 루브릭, 부트스트랩 구간, 쌍체 비교, 최소 검출 차이 |
| 실험 러너 | `pipeline.py`. 같은 후보 공유, 이어 돌리기, 설정·데이터·시드 불일치 시 거부, 환경 기록, 조건×분할 요약과 기준선 대비 비교 |
| 보호 장치 | test 분할은 기본 제외(`--final-test`로만 포함), 튜닝 함수가 test를 거부, 경험 기록이 test를 거부, 저장소의 비밀키 검사 |
| 실행 환경 | Colab 노트북(한 셀), GitHub Actions(3.10/3.11/3.12), Gradio 데모, `configs/default.json`을 읽는 `--config` |
| 협업 | `docs/BOUNDARIES.md`(파일별 담당), `docs/PROTOCOL.md`(사전 등록·분할·통계·보고 규칙), `CLAUDE.md`, PR 템플릿 |

원문서 7절과 달라진 점: `KnowledgeItem`에 `retrieval_score`, `selection_score`, `reliability`, `lang`을 추가했다. `evaluate`는 `answer=None` 인자를, `retrieve`는 `domains=None` 인자를 더 받는다. 기존 호출은 그대로 동작한다.

### 구현하면서 발견해서 고친 결함 세 건

1. **일부 줄만 깨진 파일을 통째로 버렸다.** JSONL에 문법 오류 한 줄이 있으면 정상 줄까지 모두 버렸다. B와 C가 올리는 데이터에서 실제로 날 수 있는 일이다. 테스트가 잡았고, 읽을 수 없는 파일과 일부만 깨진 파일을 구분하게 고쳤다.
2. **다양성 보너스가 관련도와 무관하게 붙었다.** 단일 분야 질문인데 무관한 다른 분야 문서가 보너스만으로 선택됐다("순수한 물의 pH"에 토성 문서). 보너스를 후보의 관련도에 비례하게 바꿨다.
3. **질문어 커버리지가 불용어도 한 단어로 셌다.** 코퍼스 IDF로 가중하게 고쳤다.

2번과 3번은 샘플을 돌려 보다가 찾았지만, 샘플에 맞춰 가중치를 조정한 게 아니라 구조를 고친 것이다. 회귀 테스트는 샘플과 무관한 인공 사례로 만들었다. 이후 기본 가중치는 건드리지 않았다.

### 수정 뒤에도 남은 약점

코퍼스가 15문서라서 'or' 같은 불용어도 문서 빈도가 낮아 IDF가 희귀어와 같아진다. 그래서 "신경성 별과 토성 중 무엇이 더 조밀한가"(q005)에서 KORE는 화학 문서를 토성 문서보다 앞에 둔다. k=3에서는 정답 근거가 그래도 들어오지만 k=2에서는 정답 근거를 놓친다. 문서가 150~300개로 늘면 줄어들 수 있는 문제지만, 확인하기 전까지는 약점으로 남는다.

### 하지 못한 것

- **Colab에서 노트북을 실제로 실행해 보지 못했다.** 로컬에서 같은 명령을 검증했을 뿐이다. `REPO_URL`을 바꿔서 한 번 돌려 봐야 한다.
- **GitHub Actions를 실제로 돌려 보지 못했다.** 워크플로 파일은 있고 로컬 명령과 같다.
- **파이썬 3.10은 이 환경에 없어서 돌리지 못했다.** 3.10 문법만 쓰도록 했고 CI 행렬에 넣었다.
- **`HFGenerator`는 실행하지 못했다.** GPU와 모델이 필요하다. 어떤 모델이 무료 Colab에서 도는지도 확인하지 못했다.
- **Gradio는 버튼을 눌러 보지 않았다.**
- **실제 데이터로 돌려 보지 못했다.** 문서 15개짜리 샘플만 있다.
- **GitHub 저장소 생성과 푸시는 하지 않았다.** A가 직접 한다.
- **Claude 유료 플랜의 모델·사용 한도는 확인하지 못했다.** 구독 화면에서 확인한다.
