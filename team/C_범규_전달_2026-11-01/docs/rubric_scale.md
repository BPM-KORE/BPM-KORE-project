# 채점 기준과 점수 해석 (범규 C)

> 목적: KORE의 자동 채점 점수가 실제로 무엇을 측정하는지, 현재 저장소의 구현과 일치하게 설명한다.
>
> 확인 기준: `kore/evaluation.py`, `kore/schemas.py`, `kore/tokenize.py`, `tests/test_evaluation.py`, `docs/CONTRACT.md`, `docs/PROTOCOL.md`의 현재 `main` 내용.
>
> 아래 예시는 코드 동작 설명용 가상 예시이며 실제 연구 질문이나 실험 결과가 아니다.

## 1. 루브릭 데이터 형식

`data/evaluation.csv`의 `rubric` 열은 다음 구분자를 사용한다.

- `|` : 서로 다른 평가 항목 구분
- `/` : 한 평가 항목 안에서 인정할 대체 표현 구분

예를 들어 `광합성|빛 에너지/빛을 이용|양분`은 평가 항목 3개를 뜻한다. 두 번째 항목은 `빛 에너지` 또는 `빛을 이용` 중 하나가 답변에 포함되면 일치한다.

이 형식은 `kore/schemas.py`의 `EvalQuestion.rubric_items()`에서 해석한다. 빈 표현은 제외하고, 남은 대체 표현을 항목별 목록으로 만든다.

## 2. 실제 점수 계산식

`kore/evaluation.py`의 `rubric_score()`는 각 평가 항목에서 대체 표현 중 하나라도 답변과 일치하는지 확인한다. 모든 항목의 비중은 같다.

\[
\text{rubric 점수} =
\frac{\text{일치한 평가 항목 수}}
{\text{전체 평가 항목 수}}
\]

평가 항목이 없으면 `None`을 반환한다. `evaluate()`는 답변이 제공되고 `rubric_items`도 있을 때만 `rubric_score`를 계산한다. 답변이 없거나 루브릭이 없으면 결과의 `rubric_score`는 `None`이다.

## 3. 코드가 실제로 하는 문자열 비교

현재 채점은 의미를 이해하는 방식이 아니라 문자열 포함 여부를 확인하는 방식이다.

1. `kore.tokenize.normalize()`가 유니코드 NFKC 정규화와 소문자 변환을 한다.
2. 답변과 각 대체 표현에 같은 정규화를 적용한다.
3. 일반 대체 표현은 정규화한 표현이 답변 문자열 안에 포함되는지 확인한다.
4. 숫자·소수점·쉼표로만 이루어진 대체 표현은 숫자 경계를 추가로 확인한다.

**정규화가 하지 않는 일도 중요하다.** 현재 `normalize()`는 문장부호 제거, 띄어쓰기 통일, 한국어 형태소 분석, 조사·어미 제거를 하지 않는다. `ngram_stem`은 검색 토크나이저의 기능이며 루브릭 채점에 적용되는 기능이 아니다.

숫자 비교는 `kore/evaluation.py`의 `_DIGITS_RE`와 정규식 경계 검사에 따른다. 테스트(`tests/test_evaluation.py`)에서 확인되는 동작은 다음과 같다.

| 답변 | 루브릭 대체 표현 | 결과 |
|---|---|---:|
| `The pH is 17.` | `7` | 불일치 |
| `The pH is 7.` | `7` | 일치 |
| `pH of 7.0` | `7` | 일치 |

따라서 `7`이 `17`에 잘못 걸리는 것은 막지만, `7`과 `7.0`을 서로 다른 값으로 구별하지는 않는다. 소수점까지 엄밀히 구분해야 하는 평가라면 루브릭에 의존하지 말고 별도 검증 기준을 설계해야 한다.

## 4. 점수 예시

다음은 실제 연구 질문이 아닌 설명용 예시다.

- 질문: 식물이 빛이 있는 곳에서 양분을 만드는 과정은 무엇이며, 빛은 어떤 역할을 하는가?
- 평가 항목: `광합성|빛 에너지/빛을 이용|양분`
- 평가 항목 수: 3개

| 답변 | 일치한 항목 | 점수 |
|---|---:|---:|
| “식물은 빛 에너지를 이용해 광합성을 하고 양분을 만든다.” | 3개 | 1.00 |
| “광합성으로 양분을 만든다.” | 2개 | 0.67 |
| “물을 많이 주면 식물이 자란다.” | 0개 | 0.00 |

항목이 3개라면 가능한 점수는 0, 0.33, 0.67, 1.00이다. 항목 수가 적을수록 한 항목이 전체 점수에서 차지하는 비중이 커진다.

## 5. 점수 해석의 한계

- **1.00은 의미상 완벽한 정답이라는 뜻이 아니다.** 등록된 문자열 조건이 모두 일치했다는 뜻이다.
- 부정 표현을 이해하지 못한다. 예를 들어 `광합성`이 루브릭에 있으면 “광합성을 하지 않는다”도 해당 문자열이 들어 있다는 이유로 일치할 수 있다.
- 조사·어미나 표현이 달라져 등록된 문자열이 포함되지 않으면, 의미상 맞는 답도 놓칠 수 있다.
- 틀린 설명과 정답 키워드가 함께 들어 있으면 점수가 높아질 수도 있다.
- 대체 표현을 너무 넓게 등록하면 오답도 통과할 수 있다. 각 대체 표현이 같은 핵심 의미를 인정하는지 검토해야 한다.

따라서 루브릭 점수는 답변 품질의 완전한 측정값이 아니라 **키워드 일치 대용 지표**다.

## 6. KORE 실험에서의 위치

`docs/PROTOCOL.md`는 주 지표를 test 분할에서 `kore`와 `vanilla_rag`의 루브릭 점수 차이로 정하고 있다. 같은 질문끼리 짝지은 평균 차이와 부트스트랩 95% 구간을 사용한다.

검색 성능과 답변 품질은 구분한다.

- `recall`, `precision`, `hit`, `mrr`: 선택한 문서가 정답 근거 문서와 얼마나 겹치는지 평가
- `rubric_score`: 생성 답변에 등록한 평가 표현이 얼마나 포함됐는지 평가
- 사람 블라인드 채점: 자동 루브릭이 의미상 답변 품질과 얼마나 맞는지 별도로 확인

사람 블라인드 채점은 자동 점수의 한계를 보완하는 절차이지, 자동 점수와 같은 값을 재는 절차가 아니다. `docs/TASKS.md`의 절차에 따라 채점자는 조건명을 가린 답변을 독립적으로 평가한다.

## 7. 질문 작성 원칙

1. 질문마다 서로 다른 핵심 내용을 확인하는 평가 항목을 2~3개 둔다.
2. 근거 문장을 그대로 복사하지 않는다. 복사하면 BM25 검색이 유리해질 수 있다.
3. 질문 문장에 정답 키워드를 그대로 넣지 않는다.
4. `reference_answer`는 짧은 한 문장으로 작성한다. 이 값은 루브릭 점수가 아니라 문서 기여도 라벨링에서 로그확률을 계산하는 데 사용된다.
5. 실제 질문은 연구 분야와 사용할 지식 문서가 승인된 뒤 작성한다. 미승인 임시 자료를 확정 평가 데이터로 취급하지 않는다.

## 8. 코드와 문서의 역할 구분

- `kore/schemas.py`: `LIST_SEP`, `ALT_SEP`, `EvalQuestion.rubric_items()`로 CSV 루브릭 형식을 해석
- `kore/tokenize.py`: NFKC 및 소문자 정규화 함수 제공
- `kore/evaluation.py`: 문자열 일치 판정과 루브릭 점수 계산
- `tests/test_evaluation.py`: 대체 표현, 숫자 경계, 기호, 대소문자, 빈 루브릭 등의 동작 확인
- `docs/CONTRACT.md`: 평가 데이터의 열과 작성 규칙
- `docs/PROTOCOL.md`: 주 지표와 사람 블라인드 평가 절차

이 문서는 설명 자료다. `kore/`의 구현 코드를 변경하거나 대체하지 않는다.
