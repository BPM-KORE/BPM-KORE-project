## 1. 확인 결과: 루브릭 점수식

실제 코드와 일치하는 식은 다음과 같다.

`rubric_score = 일치한 평가 항목 수 / 전체 평가 항목 수`

- `EvalQuestion.rubric_items()`는 `|`로 항목을 나누고 `/`로 대체 표현을 나눈다.
- `normalize()`는 NFKC 정규화와 소문자 변환만 한다.
- 일반 표현은 정규화한 문자열의 포함 여부로 판단한다.
- 숫자·소수점·쉼표로만 구성된 대체 표현은 숫자 경계를 추가 검사한다.
- 테스트는 `7`이 `17`에는 일치하지 않지만 `7.0`에는 일치하는 동작을 확인한다.
- 루브릭 항목이 없으면 `None`이며, 답변이 없을 때도 루브릭 점수를 계산하지 않는다.

따라서 자동 루브릭은 의미 평가가 아닌 문자열 일치 대용 지표다. 이전 문서의 핵심 계산식은 틀리지 않았지만, 숫자 경계와 정규화가 하는 일을 더 구체적으로 적었다.

## 2. 확인 결과: 기여도 계산식

현재 `kore/labeling.py`는 각 문서 부분집합에 대해 `scorer.score(question, evidence, reference_answer)`를 호출한다. 실제 `HFGenerator.score()`는 정답 문장의 토큰별 로그확률을 구한 뒤 토큰 수로 나눈 평균 로그확률을 반환한다.

기호를 다음과 같이 둔다.
- `s(∅)`: 근거 문서가 없을 때 reference_answer의 평균 로그확률
- `s(a)`: 문서 a만 제공했을 때의 평균 로그확률
- `s(a,b)`: 문서 a와 b를 함께 제공했을 때의 평균 로그확률

코드의 계산은 다음과 같다.

`단일 기여도 g(a) = s(a) - s(∅)`

`두 문서 조합 효과 synergy(a,b) = s(a,b) - s(a) - s(b) + s(∅)`

이는 답변의 사실적 정확도나 사람 평가 점수가 아니다. 한 모델·한 프롬프트·한 reference_answer 표현에서 그 문장이 얼마나 그럴듯한지의 차이를 보는 대용치다.

## 3. 코드 기본값과 실험 계획의 구분

- `label_question()`의 코드 기본값: 후보 최대 8개, 부분집합 크기 최대 3.
- `docs/PROTOCOL.md` 및 `docs/DECISIONS.md`의 초기 H1 단계: 후보 6개, 부분집합 크기 2까지.
- 초기 단계에서 H1 신호가 있을 때 확장: 후보 8개, 부분집합 크기 3까지.
- 라벨링 허용 분할은 `train`, `dev`이며 `test`는 금지한다.

따라서 코드 기본값을 그대로 모든 실험에 적용한다고 쓰면 부정확하다. 실제 실행에서는 프로토콜의 단계별 설정을 따라야 한다.
